## 3. POLICY STATEMENTS

### 3.1 Audit Event Logging — NIST 3.3.1 (AU-2)

**3.1.1 Audit Events to Be Logged (ODP-AU-1)**

CyberHygiene shall log the following audit events on all CPN systems:

**Category 1: Access Control Events**
- Successful and failed login attempts (local, SSH, FreeIPA)
- User account creation, modification, deletion
- Group membership changes
- Privilege escalation (sudo usage)
- Authentication failures (failed password, failed MFA)
- Session establishment and termination

**Category 2: File and Object Access**
- CUI file access (read, write, delete) — via auditd file watches
- Configuration file modifications (`/etc/`)
- System binary modifications (`/usr/bin/`, `/usr/sbin/`)
- Critical directory access (`/boot/`, `/lib/modules/`)
- Permission changes (chmod, chown)

**Category 3: System Administration**
- Software installation, update, removal (dnf, rpm)
- Service start, stop, restart (systemd)
- Firewall rule changes (firewalld, nftables)
- System configuration changes (sysctl, kernel parameters)
- Time synchronization changes (chrony, NTP)

**Category 4: Security Events**
- Security policy changes (SELinux mode, policy updates)
- Audit configuration changes (auditd rules)
- Cryptographic operations (key generation, certificate operations)
- Security alerts from Wazuh SIEM
- Malware detections (ClamAV, YARA)
- File integrity monitoring alerts (Wazuh FIM)

**Category 5: Network Activity**
- Network connections (inbound SSH, outbound HTTPS)
- Firewall denials and accepts (logged by pfSense)
- DNS queries (if DNS server role active)
- TLS/SSL handshakes and failures

**Category 6: System Events**
- System startup and shutdown
- Kernel module loading/unloading
- Hardware changes (device add/remove)
- System errors and crashes

**3.1.2 Audit Event Implementation**

Audit events are logged via:
- **auditd:** Kernel-level audit framework (comprehensive file/system event logging)
- **rsyslog:** System logging daemon (application logs, authentication logs)
- **Wazuh agent:** Security event aggregation and correlation
- **Application logs:** Apache, FreeIPA, PostgreSQL (if applicable)

**Audit Event Inventory:** Detailed audit event list documented in `/home/sysadmin/CyberSecurity/Rev3/Evidence/Audit_Event_Inventory_v1.0.md` (to be created Phase 3)

### 3.2 Audit Event Content — NIST 3.3.2 (AU-3)

**3.2.1 Required Audit Record Content**

Each audit record shall contain at minimum:

a) **Event type** — What happened (e.g., "login", "file access", "privilege escalation")

b) **Timestamp** — When event occurred (synchronized via NTP, accurate to ±1 second)

c) **Event outcome** — Success or failure

d) **User/subject identity** — Who performed the action (UID, username, process ID)

e) **Object identity** — What was acted upon (filename, IP address, service name)

f) **Source** — Where event originated (hostname, source IP, terminal)

g) **Additional context** (where applicable):
   - Command executed (for sudo events)
   - File permissions before/after (for chmod/chown)
   - Old/new values (for configuration changes)

**3.2.2 Audit Record Format**

Audit records use standard formats:
- **auditd:** Kernel audit format (type=EVENT_TYPE msg=audit(timestamp:serial): ...)
- **rsyslog:** Syslog format (RFC 5424)
- **Wazuh:** JSON format (structured, machine-parseable)

**Example auditd record:**
```
type=SYSCALL msg=audit(1710774000.123:45678): arch=c000003e syscall=2 success=yes exit=3 a0=7fffc4e8b9a0 a1=0 a2=1b6 a3=0 items=1 ppid=12345 pid=12346 auid=1000 uid=1000 gid=1000 euid=1000 suid=1000 fsuid=1000 egid=1000 sgid=1000 fsgid=1000 tty=pts0 ses=23 comm="cat" exe="/usr/bin/cat" key="cui_access"
```

### 3.3 Audit Review, Analysis, and Reporting — NIST 3.3.3 (AU-6)

**3.3.1 Audit Review Frequency (ODP-AU-2)**

Audit logs shall be reviewed:

a) **Real-time automated review (Daily):**
   - Wazuh SIEM monitors all audit logs continuously
   - High-severity alerts trigger immediate email notifications
   - Dashboard provides real-time security event visibility
   - **Exceeds DoD baseline** (DoD ODP: Weekly manual review)

b) **Manual review (Weekly):**
   - System Owner reviews Wazuh dashboard weekly
   - Review high-severity alerts and trends
   - Investigate anomalies or suspicious patterns
   - Document review in audit log review record

**3.3.2 Audit Analysis Procedures**

Weekly audit review shall include:

1. **Review Wazuh Dashboard:**
   - Navigate to: https://dc1.example.local:443/app/wazuh
   - Review "Security Events" dashboard
   - Check "Top 10 Alerts" widget
   - Review "Failed Authentication Attempts" widget

2. **Investigate Anomalies:**
   - Unexpected login locations (non-192.168.1.x IPs)
   - Failed authentication spikes (>10 failures/hour)
   - Privilege escalation by unauthorized users
   - File integrity monitoring alerts (unexpected file changes)
   - Unusual sudo usage patterns

3. **Generate Reports:**
   - Export weekly summary from Wazuh
   - Document findings (normal activity vs. incidents)
   - Escalate incidents per TCC-IRP-001

4. **Document Review:**
   - Record review date, reviewer, findings
   - Maintain review log: `/var/log/audit/review_log.txt`

**3.3.3 Automated Alerting**

Wazuh SIEM provides automated alerting for:
- **Level 10+ alerts** (Critical) — Immediate email notification
- **Level 7-9 alerts** (High) — Email notification, investigate within 24 hours
- **Level 4-6 alerts** (Medium) — Review during weekly manual review
- **Level 1-3 alerts** (Low/Info) — Logged, no action required

**Alert Configuration:** `/var/ossec/etc/ossec.conf` on dc1 (Wazuh manager)

### 3.4 Audit Log Reduction and Report Generation — NIST 3.3.4 (AU-7)

**3.4.1 Log Reduction Capabilities**

Wazuh SIEM provides log reduction and analysis:

a) **Filtering:**
   - Filter by severity level (Critical, High, Medium, Low)
   - Filter by event type (authentication, file access, network, etc.)
   - Filter by time range (last hour, last 24 hours, last 7 days, custom)
   - Filter by system (dc1, workstation1, workstation2, workstation3)

b) **Aggregation:**
   - Group similar events (e.g., "50 failed SSH attempts from 1.2.3.4")
   - Correlation rules link related events (e.g., "failed login → successful login 2 minutes later")

c) **Reporting:**
   - Pre-built reports: Security events, compliance (PCI-DSS, GDPR, NIST 800-171)
   - Custom reports via Wazuh API
   - Scheduled reports (daily/weekly email summaries)

**3.4.2 Report Generation**

Reports shall be generated:
- **Weekly:** Security summary report (emailed to System Owner)
- **Monthly:** Compliance report (NIST 800-171 Rev 3 coverage)
- **On-demand:** Incident investigation reports (when incidents occur)
- **Annually:** Annual audit log analysis (for risk assessment)

### 3.5 Response to Audit Logging Process Failures — NIST 3.3.5 (AU-5)

**3.5.1 Audit Failure Actions**

If audit logging fails, the system shall:

a) **Alert administrators:**
   - auditd failure triggers Wazuh alert (Level 10 - Critical)
   - Email sent to System Owner immediately
   - Dashboard notification

b) **Take protective action (ODP-AU-5):**
   - **Disk full:** auditd configured with `disk_full_action=HALT`
   - System halts if audit disk space exhausted (prevents continuing without audit trail)
   - **Disk low space:** auditd sends alert at 75% capacity (`space_left_action=EMAIL`)
   - **Service failure:** systemd attempts restart (3 attempts), then alerts

c) **Document failure:**
   - Audit failure logged in system logs (rsyslog, Wazuh)
   - Incident documented per TCC-IRP-001

**3.5.2 Audit Disk Space Management**

To prevent audit disk exhaustion:
- **Disk allocation:** `/var/log/audit` on separate partition (or monitored volume)
- **Disk space monitoring:** Wazuh monitors disk space, alerts at 75% full
- **Log rotation:** auditd rotates logs when reaching size limit (`max_log_file = 100MB`)
- **Log retention:** 90 days local retention, then archived to Wazuh (1 year) and encrypted backups (indefinite)
- **Automated cleanup:** Logs older than 90 days rotated out, archived to Wazuh

**Configuration:** `/etc/audit/auditd.conf`
```
max_log_file = 100
num_logs = 30
space_left = 750MB
space_left_action = EMAIL
admin_space_left = 500MB
admin_space_left_action = HALT
disk_full_action = HALT
disk_error_action = HALT
```

### 3.6 Audit Record Time-Stamps — NIST 3.3.6 (AU-8)

**3.6.1 Time Synchronization**

All CPN systems maintain accurate time via:

a) **NTP synchronization:**
   - **Service:** chrony (NTP client/server)
   - **NTP servers:** pool.ntp.org (public NTP pool)
   - **Sync frequency:** Every 64 seconds (default chrony polling)
   - **Accuracy:** ±1 second (sufficient for audit correlation)

b) **Time source validation:**
   - chrony verifies NTP server authenticity (NTP authentication if configured)
   - Rejects time updates from stratum >10 servers (too inaccurate)
   - Gradual time adjustment (slew) for small differences, step for large (>1000 seconds)

c) **Monitoring:**
   - Wazuh monitors chrony service status
   - Alert if chrony service stops or time drift >5 seconds
   - OpenSCAP validates NTP configuration (rule: `xccdf_org.ssgproject.content_rule_chronyd_or_ntpd_set_maxpoll`)

**3.6.2 Timestamp Format**

Audit record timestamps use:
- **Format:** Unix timestamp (seconds since epoch) + milliseconds
- **Timezone:** UTC (recommended) or local time with timezone offset
- **Example:** `1710774000.123` = March 18, 2026 14:20:00.123 UTC

**3.6.3 Time Source Availability**

If NTP servers unavailable:
- System continues using local clock (may drift over time)
- Wazuh alert generated (NTP sync failure)
- System Owner investigates and restores NTP connectivity
- Audit records continue to be generated (with potentially inaccurate timestamps)

### 3.7 Protection of Audit Information — NIST 3.3.7 (AU-9)

**3.7.1 Audit Log Protection**

Audit logs are protected from unauthorized access, modification, and deletion:

a) **File permissions:**
   - `/var/log/audit/` owned by root:root
   - Permissions: `0600` (rw-------)  — Only root can read/write
   - `/var/log/audit/audit.log` — active log file
   - `/var/log/audit/audit.log.1` through `.30` — rotated log files

b) **Immutability:**
   - auditd configured with `log_format = RAW`
   - Once written, audit records cannot be modified
   - SELinux protects `/var/log/audit/` (type: `auditd_log_t`)
   - Only auditd process (with `auditd_t` context) can write

c) **Centralized logging:**
   - Wazuh agent forwards audit logs to Wazuh manager (dc1) in real-time
   - Centralized logs protected on Wazuh manager (separate system)
   - If local system compromised, centralized logs preserved

d) **Backup:**
   - Audit logs included in daily encrypted backups to NAS
   - Backups stored off-system (cannot be deleted by compromised system)
   - Retention: Indefinite (encrypted, 3-2-1 backup strategy)

**3.7.2 Audit Configuration Protection**

Audit configuration files are protected:
- `/etc/audit/auditd.conf` — auditd configuration
- `/etc/audit/rules.d/*.rules` — audit rules
- Permissions: `0640` (rw-r-----) root:root
- Changes logged by auditd itself (watch on `/etc/audit/`)
- Changes require root access (sudo)

**3.7.3 Restrictions on Audit Log Management**

Only authorized administrators (root, sysadmin with sudo) can:
- Modify audit configuration
- Delete audit logs (discouraged; archives preferred)
- Disable audit logging (requires reboot with `audit=0` kernel parameter)

Unauthorized users:
- Cannot read `/var/log/audit/` (permission denied)
- Cannot modify audit logs (permission denied, SELinux enforced)
- Cannot disable auditd (insufficient privileges)

### 3.8 Audit Record Retention — NIST 3.3.8 (AU-11)

**3.8.1 Retention Period (ODP-AU-3)**

Audit logs shall be retained:

a) **Local retention (90 days):**
   - Location: `/var/log/audit/`
   - Format: Raw audit logs (auditd format)
   - Rotation: 30 files × 100MB each ≈ 3GB ≈ 90 days at current volume
   - Purpose: Immediate access for investigations

b) **Centralized retention (1 year):**
   - Location: Wazuh manager (dc1) — `/var/ossec/logs/archives/`
   - Format: JSON (structured)
   - Retention: 365 days
   - Purpose: Long-term analysis, compliance reporting
   - **Meets DoD ODP baseline** (DoD ODP: 1 year)

c) **Archived retention (Indefinite):**
   - Location: Encrypted NAS backups
   - Format: Compressed, encrypted
   - Retention: Indefinite (until no longer needed for investigations/audits)
   - Purpose: Long-term preservation for legal/regulatory requirements

**3.8.2 Retention Justification**

- **90 days local:** Sufficient for most investigations (recent incidents)
- **1 year centralized:** Meets DFARS, NIST 800-171, audit requirements
- **Indefinite archive:** Supports multi-year audits, legal holds, historical analysis

**3.8.3 Disposition**

Audit logs beyond retention periods:
- Local logs (>90 days): Automatically rotated out (oldest deleted when disk space needed)
- Centralized logs (>1 year): Archived to backup, then deleted from Wazuh indexer
- Archived logs: Retained until no longer needed, then securely deleted (NIST 800-88 sanitization)

### 3.9 Audit Record Generation — NIST 3.3.9 (AU-12)

**3.9.1 Audit Capability Scope**

CyberHygiene systems generate audit records for:

a) **All systems processing CUI:**
   - dc1, workstation1, workstation2, workstation3 (100% coverage)

b) **All audit events defined in Section 3.1.1:**
   - Access control, file access, system administration, security events, network activity, system events

c) **All users:**
   - System owner/administrator (sysadmin)
   - Service accounts (apache, wazuh, freeipa, postgres)
   - Root user (when sudo used)

**3.9.2 Audit Generation Limitation**

To avoid overwhelming audit logs with low-value events:

a) **Excluded events (not logged):**
   - Routine read-only access to non-CUI files (e.g., `/usr/share/doc/`)
   - Automated system processes (cron jobs) unless they modify critical files
   - High-frequency benign events (e.g., systemd service status checks)

b) **Audit rule scoping:**
   - File watches limited to CUI directories (`/cui/`, `/home/*/CUI/`)
   - System binary watches limited to changes (not reads)
   - Network logging limited to inbound connections (not every outbound DNS query)

**Justification:** Balance security visibility with storage/performance. Focus on security-relevant events.

**3.9.3 Audit Generation Availability**

Audit generation is mandatory and cannot be disabled by users:
- auditd starts at boot (systemd service: `auditd.service`, enabled)
- Kernel audit compiled into kernel (`CONFIG_AUDIT=y`)
- Disabling requires kernel parameter `audit=0` (requires root, reboot, GRUB access)
- Wazuh agent starts at boot (systemd service: `wazuh-agent.service`, enabled)

## 5. PROCEDURES

### 5.1 Weekly Audit Review Procedure

**Frequency:** Weekly (every Monday, 9:00 AM)

**Steps:**

1. **Access Wazuh Dashboard:**
   - URL: https://dc1.example.local:443/app/wazuh
   - Login with admin credentials

2. **Review Security Events (last 7 days):**
   - Navigate to "Security Events" module
   - Review "Top 10 Alerts" widget
   - Check for Level 7+ (High/Critical) alerts

3. **Review Specific Categories:**
   - **Authentication:** Review "Authentication" dashboard
     - Check failed login attempts (threshold: >10 failures unusual)
     - Verify all successful logins from expected IPs (192.168.1.x)
   - **File Integrity:** Review "File Integrity Monitoring" dashboard
     - Investigate any unexpected file changes in `/etc/`, `/usr/bin/`
   - **Vulnerability Detection:** Review "Vulnerabilities" dashboard
     - Check for new CVEs in installed packages

4. **Investigate Anomalies:**
   - If anomaly detected, drill down into individual events
   - Correlate events across systems
   - Determine if incident or false positive

5. **Document Review:**
   - Record review date, findings, actions taken
   - Append to `/var/log/audit/review_log.txt`:
     ```
     [2026-03-18] Weekly audit review completed by sysadmin.
     Findings: 2 failed SSH attempts from 203.0.113.5 (expected, blocked by firewall).
     1 sudo privilege escalation (expected, package update). No incidents.
     ```

6. **Escalate Incidents (if needed):**
   - If security incident identified, follow TCC-IRP-001

**Time Required:** 30-60 minutes per week

### 5.2 Audit Configuration Change Procedure

**When to Use:** Adding new audit rules, modifying auditd configuration

**Steps:**

1. **Identify need for change:**
   - New CUI data location to monitor
   - New security requirement (e.g., watch specific command)
   - Performance tuning (reduce log volume)

2. **Draft audit rule:**
   - Syntax: `-w /path/to/file -p permissions -k key_name`
   - Example: `-w /home/sysadmin/CUI/ -p wa -k cui_access`
     - `-w` = watch path
     - `-p wa` = log writes (w) and attribute changes (a)
     - `-k cui_access` = key for filtering

3. **Test rule:**
   - Add rule temporarily: `auditctl -w /test/path -p wa -k test`
   - Trigger event: `echo test > /test/path/file`
   - Verify logged: `ausearch -k test`
   - Remove test rule: `auditctl -W /test/path -p wa -k test`

4. **Implement permanently:**
   - Add rule to `/etc/audit/rules.d/99-custom.rules`
   - Reload rules: `augenrules --load` or reboot

5. **Verify:**
   - Check rules active: `auditctl -l | grep <key_name>`
   - Monitor Wazuh for events with new key

6. **Document:**
   - Update Audit Event Inventory (Phase 3 deliverable)
   - Note change in audit configuration change log

---

### 5.3 Audit Disk Space Management Procedure

**When to Use:** Responding to low disk space alerts

**Steps:**

1. **Receive alert:**
   - auditd sends email when disk space reaches 75% (space_left threshold)
   - Wazuh alert: "Low disk space on /var/log/audit"

2. **Check disk usage:**
   ```bash
   df -h /var/log/audit
   du -sh /var/log/audit/*
   ```

3. **Identify oldest logs:**
   ```bash
   ls -lth /var/log/audit/audit.log.*
   ```

4. **Archive old logs (optional):**
   ```bash
   # Compress and move to archive location
   gzip /var/log/audit/audit.log.25
   mv /var/log/audit/audit.log.25.gz /archive/audit/
   ```

5. **Force rotation (if needed):**
   ```bash
   service auditd rotate
   ```

6. **Verify space recovered:**
   ```bash
   df -h /var/log/audit
   ```

7. **Long-term fix (if recurring):**
   - Increase audit partition size
   - Reduce num_logs (fewer rotated logs kept)
   - Archive to centralized storage more frequently

## 7. DEFINITIONS

**Audit Logging:** Recording of system events and activities for security monitoring, investigation, and compliance.

**Audit Record:** A single entry in an audit log documenting an event (timestamp, user, action, outcome).

**Audit Reduction:** Filtering or aggregating large volumes of audit records to identify relevant events.

**Centralized Logging:** Forwarding logs from multiple systems to a central SIEM for analysis and long-term retention.

**Organization-Defined Parameter (ODP):** A variable in Rev 3 controls that organizations must define (e.g., audit retention period).

## APPENDIX A: AUDIT RULE EXAMPLES

### Example 1: Monitor CUI File Access
```bash
# Watch CUI directory for writes and attribute changes
-w /home/sysadmin/CUI/ -p wa -k cui_access

# Explanation:
# -w /path = watch path
# -p wa = permissions: w(rite), a(ttribute change)
# -k key_name = searchable key for ausearch/Wazuh
```

### Example 2: Monitor Privileged Commands
```bash
# Log all sudo usage
-a always,exit -F arch=b64 -S execve -F euid=0 -F auid>=1000 -k privileged

# Explanation:
# -a always,exit = log on syscall exit
# -F arch=b64 = 64-bit architecture
# -S execve = execve syscall (program execution)
# -F euid=0 = effective UID is root
# -F auid>=1000 = original UID is user (not system service)
# -k privileged = key for filtering
```

### Example 3: Monitor Configuration Changes
```bash
# Watch /etc/ for any changes
-w /etc/ -p wa -k config_changes

# Watch specific critical configs
-w /etc/ssh/sshd_config -p wa -k sshd_config
-w /etc/audit/auditd.conf -p wa -k audit_config
-w /etc/firewalld/ -p wa -k firewall_config
```

### Example 4: Monitor System Binary Modifications
```bash
# Watch system binary directories for changes (not reads)
-w /usr/bin/ -p wa -k system_binaries
-w /usr/sbin/ -p wa -k system_binaries
-w /usr/lib64/ -p wa -k system_libraries
```
